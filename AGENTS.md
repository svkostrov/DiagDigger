## Назначение проекта

DiagDigger — локальный web-сервис для просмотра и сравнения файлов самодиагностики роутеров и ретрансляторов Keenetic/Netcraze. Пользователь загружает один или несколько self-test файлов и получает структурированное представление вместо необходимости читать большой сырой текст.

Главная ценность проекта — смысловое представление и сравнение конфигураций. Сервис должен показывать не только различия строк, а понятные факты: на одном устройстве есть Wi‑Fi 5 ГГц, на другом нет; PPPoE настроен только слева; параметры WireGuard отличаются по endpoint, allowed networks, MTU и другим полям.

Все данные обрабатываются в браузере. Ничего из диагностик не отправляется на сервер. Не добавлять аналитику, внешнее хранение или сетевую передачу содержимого без прямого согласования с пользователем.

## Обязательные требования пользователя

- Поддерживать разные модели, версии прошивки, роли `router`/`extender` и различающийся состав секций.
- Не считать отсутствующую секцию ошибкой. Неизвестные данные сохранять и показывать в категории «Прочее».
- Основной просмотр разбивать по понятным категориям: система, интернет, интерфейсы и сегменты, Wi‑Fi, VPN и туннели, маршрутизация, DHCP/DNS, безопасность, сервисы, логи, процессы, память, оборудование и прочее.
- Конфигурацию дополнительно разбирать на смысловые объекты, а не показывать только целиком.
- Основное сравнение — смысловое и категорийное. Сырой diff оставлять дополнительным режимом для инженера.
- Наглядно показывать наличие/отсутствие возможностей и объектов, а также отличающиеся параметры.
- Интерфейс должен быть визуально близок к web-интерфейсу Netcraze/Keenetic: фирменная синяя акцентная палитра, верхняя панель, левое двухуровневое меню, карточки и плотные таблицы.
- Поддерживать светлую, тёмную и автоматическую темы. Авто следует системной теме, выбор сохраняется после перезагрузки; переключатель темы показывать широким выпадающим полем с подписью «Стиль оформления» в нейтральной рамке.
- Меню должно учитывать содержимое выбранной диагностики: пустые категории и группы не показывать.
- Номер версии приложения показывать в верхней панели рядом с названием. Текущая версия — `2.1`; при каждом изменении проекта увеличивать версию и синхронно обновлять видимую подпись, `package.json` и `package-lock.json`.
- После завершения любых изменений обязательно создавать Git-коммит и отправлять текущую ветку в настроенный remote (`git push`). Не оставлять завершённые изменения только локально.
- В обычной задаче запускать только быстрые и точечные проверки. Полный долгий `npm run test:ui` не запускать: им занимается отдельный агент; использовать лишь конкретные Playwright-сценарии, непосредственно относящиеся к изменению.
- Отвечать пользователю по-русски, коротко и без лишней воды. Не придумывать формат данных: при неоднозначности сначала изучить реальные файлы или уточнить.

## Текущая архитектура

Проект — статическое ES-module приложение без сборщика и runtime-зависимостей.

- `index.html` — каркас страницы, загрузка файлов, верхняя панель, переключатель темы, workspace.
- `app.js` — состояние приложения, загрузка файлов через File API, рендеринг, навигация, поиск, просмотр секций и оба режима сравнения.
- `parser.js` — извлечение `<file>`-секций, разбор имени файла, категоризация, разбиение `ndm:sharing-config`, построение смысловых объектов и алгоритмы сравнения.
- `styles.css` — базовые стили и токены.
- `semantic.css` — представление смыслового сравнения.
- `netcraze.css` — основной тёмный Netcraze-подобный слой и левое меню.
- `themes.css` — переключатель тем и переопределения светлой темы.
- `Dockerfile`, `nginx.conf`, `compose.yaml` — production-запуск статического
  приложения в Docker через Nginx; сервис по умолчанию доступен на порту 4173.
- `tests/parser.test.js` — unit-тесты парсинга и сравнения.
- `tmp/pdfs/` — локальные копии CLI-мануалов, используемые как справочник.

`parser.js` возвращает объект диагностики с `meta`, исходным `text`, подготовленным `searchText`, кэшем поисковых запросов, массивом `sections` и массивом `semantic`. Секции используются для просмотра и сырого diff. Помимо `<file>`, весь исходный self-test сохраняется как секция «Структурированные данные self-test» в категории «Прочее», поэтому неизвестные XML-узлы не теряются даже в невалидном XML. Узлы `<error>` дополнительно собраны в отдельную секцию «Ошибки сбора диагностики». Все XML-выводы команд `show` выделяются в производные разделы; известные команды получают специальные категории и представления, остальные сохраняются под исходным именем команды в подходящей категории или в «Прочем». `show version` дополняет метаданные `hw_id`, region, release, sandbox, NDM/BSP exact и даты. Все отображаемые и копируемые секции, а также раскрываемые `raw`-блоки смысловых объектов проходят общую очистку от паролей, ключей и идентификаторов аутентификации. Полный текст и каждая секция санитизируются один раз; санитизация сохраняет число строк, заменяя секрет заглушкой, поэтому номера строк поиска совпадают с исходным файлом.

Самостоятельные секции с валидным JSON получают структурированное представление: массивы однотипных объектов показываются таблицей, объекты — группами полей, вложенные большие значения раскрываются отдельно. Исходный санитизированный JSON всегда остаётся доступен и копируется без изменения; невалидный или смешанный с произвольным текстом JSON показывается как сырой текст. XML-выводы `show ip policy`, `show ip route`, `show ipv6 route`, `show ip dhcp pool` и `show system cpustat` показываются понятными таблицами. Для `show device-list`, `show ip neighbour`, `show ntce hosts`, `show ip arp` и `show ip http proxy` используются предметные карточки, остальные XML-выводы `show` получают общий карточный fallback. Исходный XML всегда доступен по раскрытию.

## Парсинг и категории

Источник конфигурации — секция `ndm:sharing-config`. Она разбивается по верхнеуровневым CLI-командам и группируется правилами `CONFIG_GROUPS`; команды `mws` и блоки `mws wlan` относятся к отдельной категории MWS, а `mws vlan` одновременно показывается в MWS и Wi‑Fi. В «Сервисах» дополнительно выделяются конфигурации SMB, SSTP, OpenConnect, WireGuard, L2TP/IPsec и IKEv2/IPsec. В карточках категорий настройки конфигурации всегда идут первыми и помечаются более жирным шрифтом, а собранные данные и статистика выводятся ниже. Исходные `<file name="…">` также категоризируются функцией `categoryFor`; `proc:driver/hw_nat/foe/binds` и `proc:fastvpn/binds` относятся к «Интернету», `sys:kernel/debug/usb/devices` — к USB. Для известных XML-команд `show` применяется точная таблица назначения в категории Интернета, оборудования, процессов, хостов, DHCP/DNS, сетевых правил, облака, IPv6, QoS, безопасности, системы и подразделы управления; `show crypto map` относится к VPN и туннелям, `show user` — к пользователям, неизвестные команды остаются в «Прочем». Температуры `WifiMaster0` и `WifiMaster1` в пользовательском выводе подписываются как `2.4 GHz` и `5 GHz`.

При расширении парсера:

1. Сначала найти реальные примеры во всех доступных диагностиках.
2. Сверить синтаксис с CLI-мануалами в `tmp/pdfs/` или актуальной официальной документацией.
3. Не привязывать правило только к одной модели или одному порядку строк без необходимости.
4. Сохранять исходный блок в `raw` для проверки результата.
5. Не выводить секреты в смысловых полях. Пароли, ключи и приватные данные не должны попадать в сводки сравнения.
6. Добавить минимальный тест на новый формат и на отсутствие объекта с другой стороны.

Текущие смысловые объекты:

- модель, код устройства, версия и роль;
- диапазоны Wi‑Fi 2,4/5/6 ГГц и параметры точки доступа;
- Bridge-сегменты, включая WAN-роль Bridge с `ip global` без создания второго смыслового объекта;
- WAN-подключения DHCP/Static;
- PPPoE;
- WireGuard, OpenVPN, L2TP, PPTP, SSTP, IPsec, GRE, EoIP, IPIP и ZeroTier.

Стабильность ключа объекта критична: одинаковая сущность в двух диагностиках должна получить одинаковый `key`. Иначе сравнение ошибочно покажет два отсутствующих объекта вместо одного изменённого. Ключи Wi‑Fi строятся по системному `WifiMaster`, WAN — по системному имени интерфейса, IPsec — по полному имени при отсутствии точного числового индекса; пользовательские `rename` и `description` в ключ не входят, но сравниваются как поля.

## Правила сравнения

Режим «Понятное сравнение» является основным. Для каждого объекта показывать:

- есть ли он слева и справа;
- состояние;
- число отличающихся полей;
- таблицу параметров с понятными русскими названиями;
- исходную конфигурацию только по раскрытию.

Режим «Сырые секции» нужен как проверочный fallback. Он сравнивает одинаковые секции и различает `same`, `changed`, `left-only`, `right-only`.

Поиск ограничен 1000 физическими совпадениями за один запрос и считает каждую пару «строка исходного файла + столбец» один раз. Если найденное место входит в собранные `config:*`/`derived:*` представления, эти представления прикрепляются к одному результату и показываются в интерфейсе, а не создают дубликаты. Вычисленные значения, которых дословно нет в исходном XML, например нормализованные температуры, ищутся непосредственно в производной секции. Усечённая выдача помечается в интерфейсе, повторный одинаковый запрос берётся из кэша. Для больших diff используется линейный алгоритм с уникальными опорными строками, чтобы не выделять квадратичную матрицу и сохранять совпадения после крупных вставок.

При добавлении нового типа сравнения обязательно проверить как минимум четыре случая: совпадает, изменён, есть только слева, есть только справа.

## Дизайн

Референс — реальные интерфейсы Netcraze/Keenetic 5.x, а не произвольная «админская» тема.

- Тёмная тема: тёмно-синий фон, чуть светлее карточки, серо-белый текст, ярко-синие активные состояния.
- Светлая тема: белая верхняя панель и карточки, светло-серый workspace/rail, чёрный текст, тот же синий акцент.
- Левое меню двухуровневое: видимые верхние группы и вложенные категории со счётчиками.
- Верхние группы используют синие векторные значки Netcraze: сетка для «Статуса», глобус для «Интернета», Wi‑Fi для «Моих сетей и Wi‑Fi», щит для «Сетевых правил», шестерёнка для «Управления».
- На узком экране меню превращается в компактную полосу с иконками.
- Не использовать тяжёлые декоративные эффекты, градиенты и случайные цвета, отсутствующие в референсе.
- Любые изменения темы проверять во всех трёх режимах: `light`, `dark`, `auto`.

## Локальная разработка и проверка

Запуск:

```bash
npm run dev
```

Приложение открывается на `http://localhost:4173/`.

Перед завершением изменения:

```bash
node --check app.js
npm test          # юнит-тесты парсера, node:test, без зависимостей
npm run test:ui   # e2e-тесты интерфейса, Playwright + Chromium
```

Запуск в Docker:

```bash
docker compose up -d --build
```

Приложение будет доступно на `http://localhost:4173/`; остановка —
`docker compose down`.

Перед первым прогоном e2e: `npm install && npx playwright install chromium`.
Готовый бинарник браузера можно указать через `PW_CHROMIUM_PATH`.
`npm run test:ui` сам поднимает статический сервер на 4173.

Правило, выведенное из трёх аудитов: **исправление по названному в отчёте месту
без проверки соседних путей вывода порождает новый дефект того же класса.**
Четыре фикса аудита 2 сделали именно это: BUG-047 → BUG-052, BUG-042 → BUG-060,
BUG-044 → BUG-057, BUG-023 → BUG-055. Перед закрытием дефекта искать тот же
паттерн во всех темах, ширинах, путях вывода и формах строки конфигурации.

Правило, добавленное аудитом 4: **новая функциональность приходит без своей проверки
и повторяет уже закрытые классы дефектов.** Три коммита после `bugfixed.md`
(структурированное представление JSON, перераспределение `show`-разделов, выбор темы
через `select`) вернули прокручиваемую область без клавиатурного доступа (класс
BUG-032 → BUG-078), интерактивную цель ниже 24 px (класс BUG-061 → BUG-077), мёртвые
стили удалённого элемента (класс BUG-012 → BUG-082) и повторную санитизацию одних и
тех же данных (класс BUG-069 → BUG-079). How to apply: добавляя экран, представление
или элемент управления, прогонять по нему весь обязательный набор UX/UI-проверок
ниже, а не только тот пункт, ради которого он сделан.

Правило про покрытие словаря: тест на восьми фикстурах не доказывает, что разбор
полон. `showCategory` даёт четыре команды в «Прочем» на фикстурах и 36 из 54 на
списке команд из справочника (BUG-087). Полноту раскладки проверять по оглавлению
`tmp/pdfs/cli_manual_nc-1812.pdf`, а не по тому, что попало в диагностики.

Для изменений UI дополнительно проверить приложение в браузере с хотя бы одним
реальным self-test. Для сравнения загрузить минимум два файла. Проверить
отсутствие ошибок и предупреждений в консоли.

Обязательный набор UX/UI-проверок (введён аудитом 3):

1. Доступность прогонять на **каждом** состоянии — обзор, категория, секция,
   поиск, оба режима сравнения, деталь, diff, пустой экран — и в обеих темах,
   а не только на первом экране.
2. Ширины проверять сеткой 320 / 360 / 390 / **768 / 820 / 900** / 1024 / 1440.
   Полосу 721–959 px пропустили два аудита подряд: брейкпоинты в CSS стоят на
   1000, 720 и 420 px, между 720 и 1000 ничего нет.
3. Контраст считать по вычисленным стилям в обеих темах. Фирменный акцент
   `#079bd8` не проходит AA ни как фон под белым текстом (3,13:1), ни как текст
   на светлом фоне (2,9:1).
4. После каждой перерисовки проверять `document.activeElement`: полная замена
   `innerHTML` сбрасывает фокус на `body`.
5. Проверять размеры целей (не меньше 24×24, WCAG 2.5.8) на каждой ширине.
6. Проверять состояния ошибки, пустоты и разрушения, а не только удачный путь.
7. **Сверять интерфейсный вывод с содержимым исходного файла**, а не только
   факт, что интерфейс что-то показал. Тест «поиск вернул N результатов» ничего
   не доказывает, если в файле этих вхождений тысячи: так BUG-052 прошёл через
   прогон «80 из 80 зелёных».

## Безопасность и данные

- Не сохранять в репозитории логины и пароли устройств.
- Не обращаться к живым роутерам без прямого запроса или разрешения пользователя.
- Не отправлять содержимое self-test во внешние сервисы.
- Считать диагностики потенциально чувствительными: там могут быть адреса, имена узлов, SSID, пользователи и ключевой материал.
- При необходимости демонстрационных fixtures заменять чувствительные значения синтетическими.
- Диагностики в `tests/fixtures/` не попадают в Git благодаря `.gitignore` и
  могут оставаться исходными. Тесты к конкретным значениям не привязаны. См.
  BUG-007 в `bugreport.md`.
- `sanitizeRaw` в `parser.js` — чёрный список шаблонов, и каждый аудит находит
  следующий (BUG-007 → BUG-026 → BUG-027 → BUG-053: `crypto ike key`). Добавляя
  разбор новой команды CLI, проверять, не задаёт ли она секрет. Надёжнее
  перевернуть правило: скрывать последний аргумент у списка команд, задающих
  ключевой материал, а не вычёркивать строки по префиксу.
